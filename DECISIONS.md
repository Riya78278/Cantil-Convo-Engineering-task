# Procurement decisions

These are implementation choices for ambiguities in v5.0 and the implemented workflows. The regression suites check the supplied worked examples and synthetic boundaries.

| Situation | Decision and rationale |
|---|---|
| Invalid facts | Zero or negative quantity, unknown plant, unsupported unit or missing estimate for a new item makes the batch line NOT_PROCESSED with a reason. In chat, ask for a correction. This prevents guessing quantities or spending authority. |
| Item identity | A valid code wins. For an invalid supplied code, flag for correction. For uncoded input, normalize abbreviations while preserving dimensions, grades, model numbers and units. If multiple viable catalogue items remain, ask in chat or flag the batch line for review. A genuinely unmatched description with an estimate becomes NEW. |
| Similar lines | Preserve different PR keys even if content is identical. Aggregate under normal clubbing rules. Reject ambiguous repeated keys with a clear reason and retain the original rows for reconciliation. |
| Date boundaries | Interpret local timestamps in Asia/Kolkata. For a lookback of N days use [date − N, date), excluding the current date because historical POs have no time. Resolve same-date POs deterministically by greatest PO number. |
| Ranking | Initial scoring choice: 40% item PO count divided by the maximum candidate count (zero when all counts are zero), 25% recency (1 within 90 days, 0.5 within 365, else 0), 15% prior contract, 10% on-time fraction and 10% quality divided by five. Break equal scores by ascending supplier ID. This favors demonstrated item experience while retaining supplier performance. For category top-ups sort by mean of normalized delivery and quality, then supplier ID. Validate against the three examples when the engine exists. |
| Prices and ceilings | Use exact decimal rates and quantities in comparisons. Present exported INR amounts to two decimal places, round half up at output. For equally priced usable contracts choose ascending contract ID. Only a contract PO consumes the shared contract ceiling. |
| Valuation versus eligibility | Valuation clause 3.1 says latest item PO. Use it even if that historical supplier is now ineligible. Independently check Active history for direct PO eligibility and use the award supplier's own reference price for emergency/spot POs. |
| Effective date and replay | Use the first line's local creation date for requirement routing. For a grouping amendment, form groups only among lines governed by the same effective policy version so later grouping rules cannot retroactively regroup earlier demand. Preserve run inputs, version history and opening balances for repeatable independent runs. |
| Run versus approval | Batch processing assigns reproducible planned PO IDs for scoring. Approval materializes the document once. Rerunning the same snapshot starts at its original balances and excludes POs generated by previous simulations. |
| Reference imports | Phase 2 stores an immutable opening baseline per database. Re-imports of identical reference files are harmless. A different reference baseline is rejected atomically so it cannot silently change earlier runs. Additional PR batches can be imported independently. |
| Intake staging | Preserve every CSV row with its row number and an optional issue. Free-text matching and missing new-item estimates are resolved in Phase 3. A valid staged row still needs engine evaluation. |
| Signed contract extraction | Automatically parse the text-based signed template in the kit and compare register terms against signed terms. Stop the import on disagreement or an unreadable schedule. Buyer-assisted entry for other document formats belongs to the later contract UI. |
| Matching implementation | Phase 3 normalizes brg/bearing, hyd/hydraulic, pneu/pneumatic and welding rod/electrode, plus incidental requester phrases. It preserves numeric order when matching dimensions and accepts an unambiguous subset of catalogue terms. Multiple candidates require review. No PR-number-specific matching is used. |
| Worked-example reconciliation | All 14 example outcomes and all three preferred rankings pass the engine checks. Use exact source rates for values. Compare PO membership relationships rather than the printed illustrative IDs. Example 6 includes two groups and example 14 includes two group values on one PO. |
| Runtime layout | Python handles import, exact decimal computation and the backend API, with PostgreSQL storage. The implemented frontend uses same-origin HTML, CSS and JavaScript. |
| Amendment interpretation | Phase 4 uses a deterministic local text parser plus an editable complete policy draft. Recognized statements become proposed rules. Every unrecognized statement remains visible and requires reviewer resolution and acknowledgement before approval. No external AI service receives source documents. Scanned PDFs require readable text. |
| Policy effective-date ties | Distinct approved versions may share an effective date. The later approved version takes precedence in the full timeline. Selecting the earlier version limits the timeline to that version, keeping the original run reproducible. |
| Review identity | Phase 5 binds policy and buyer actions to the authenticated username and event time. Caller-supplied actor names cannot replace the session identity. |
| Chat intake | One item per conversation. Catalogue candidates and explicit confirmation prevent invented item codes. Unknown items require explicit new-item acknowledgement, units and an estimate. Urgent maps to Emergency and is shown for confirmation. Weekdays resolve to the next occurrence after today in Asia/Kolkata. |
| Live approval ledger | Batch simulations retain imported opening balances. Actual approvals consume a separate contract ledger, used for subsequent pending chat evaluations and checked atomically on award. A PR key is awarded at most once across runs. |
| Live grouping after approval | Pending confirmed chats are evaluated together. Previously approved requests keep their original document. Later demand enters the next pending workset. Complete CSV batches continue to use the policy's full chronological grouping. |
| Overrides and consolidation | Overrides retain original evidence and require a written reason. Overridden requirements are placed on separate documents. Unmodified recommendations sharing a planned PO within a run retain that consolidation. |
| Capex approval record | A buyer must explicitly acknowledge capex approval when materializing the sourcing document. The actor and acknowledgement are recorded. A separate organizational capex approval hierarchy was not specified. |
| Hosting | Preserve the tested Python engine in a Docker web service on Render. Use Neon PostgreSQL and TLS with credentials stored only in private environment settings. Standard Neon access is credential-protected, not private-network-only. Public GitHub contains code and docs, never the raw task data or practice exports. |
| Deployment initialization | Create schema idempotently on startup without importing reference files or resetting data. Import the kit privately using the bootstrap command. New deployments begin with v5.0; amendments are approved through the app. |
| Freeze | Disable automatic redeploys so submission-file pushes do not deploy code. The organizer's actual cutoff governs changes; conflicting weekday/date labels must be clarified, not inferred from this repository. |
